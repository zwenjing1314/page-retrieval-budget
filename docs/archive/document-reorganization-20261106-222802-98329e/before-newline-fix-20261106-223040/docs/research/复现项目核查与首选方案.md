# 页面检索：复现项目核查与首选方案

核查日期：2026-11-05；2026-11-06 补充保险子集移除、数据覆盖与版本层级说明。目的：核实推荐论文和作者代码，选择一套适合 Windows、RTX 3080 Ti 约 12GB、约两个月研究周期的首次复现底座。

## 1. 本轮决定：先复现完整项目，再讨论改进

**首选 Visual RAG Toolkit，先沿用 ColPali-v1.3 和作者使用的一个官方 ViDoRe v2 子任务，复现“完整向量检索”和“一种现成池化的两阶段检索”。** 这是有条件的推荐：代码和数据确实存在，但下面已找到的标签问题必须先修正，运行环境仍需实测。

**接续澄清：Toolkit 是首选复用底座，不是已经验证兼容的最终框架，更不代表我们已经选择研究两阶段搜索。** 针对用户对后续兼容性的疑问，建议在承诺完整 A/B 复现前，先验收“完整向量检索能运行、页面向量能独立保存、替换为一种现成压缩输出后能评分、压缩索引确实只保存压缩表示”。两阶段 A/B 可用于理解作者方法，但不必先做完其全部模型、数据集和速度实验，才能开始压缩基线研究。以下配置仍是候选执行方案，本轮没有运行。

《Towards Storage-Efficient Visual Document Retrieval》v1 的 §5.1 明确讨论输出向量上的免训练 1D/2D 空间池化和语义聚类，§5.2 则另行研究训练阶段也使用合并向量，§5.3 比较模型内部与最终投影后的合并位置。因此：

- 复用 Toolkit 的模型输出入口，补一个“每页 N×128 → K×128”的压缩步骤，再复用页面 MaxSim 和评价，是合理的接法；现有代码并未提供这篇论文所有压缩设置的一键复现。
- 忠实复现还要对齐 checkpoint、数据、token 保留、归一化、合并规则和评价协议；在 ColPali-v1.3/Economics 上实现相同思想，不等于复现原论文对应表格。
- 最终 Light-ColPali/ColQwen2 包含微调；中间层合并、注意力剪枝需要模型内部信息。它们超出仅替换输出压缩函数的范围。
- 逐页固定或可变向量数量符合多向量检索接口；真实跨页共享码本需要“代表只存一次、页面存引用”的结构。当前 Qdrant 建库为每页保存实际向量，重复写同一质心不产生共享存储收益，不能保证跨页候选只需小改。
- 为减少以后迁移损失，后续应增加小型、独立的编码缓存导出：保留模型和 processor 版本、完整有效 token 输出及视觉/查询筛选掩码、页面 ID/真实 doc-id、网格信息和归一化规则。已有接口能提供部分这些内容，但缓存格式与导出尚未实现。只改压缩时可以复用缓存；换模型、预处理或需要未保存的中间信息时仍需重编码。研究用原始缓存与在线压缩索引分开记账，同时报告总磁盘占用。

同意把近期行动目标改为完整项目复现。官方数据已包含页面图像、候选库和相关性标签，没必要为了复用旧材料，先把 SciEGQA 自行改造成新基准。用户已表示后续可以下载新数据；本轮只读取公开源码、论文及小型元数据，没有下载数据集或模型。

本文件接续《启动核查.md》，**替代其“下一步只做合成码本诊断”的行动建议**。前轮有关朴素跨页共享机制的重合和成本判断仍保留。跨页共享、按可压缩性分配容量都没有在本轮立项，也不同时启动。

两项工作的名字保持明确：旧 layoutpatch 是“给定正确页和固定区域的证据区域排序”；本目录是“完整候选库中的页面检索”。首次复现现成检索流程属于页面检索的准备工作，不是已经完成新方法，更不改变毕业论文章节与研究完成顺序的区别。

### 证据怎么读

- **[源码/元数据核实]**：本轮直接读取作者源码、官方数据/模型卡和服务器元数据；证明内容存在，不证明本机能运行。
- **[论文报告]**：作者论文中的实验、速度、训练资源；不是我们的复现结果。
- **[小型函数核查]**：仅运行提取出来的标签归一化函数，未加载模型、向量或检索结果。
- **[推导/建议]**：维度、字节和复杂度计算，或下一步执行建议；不是实测或批准的方法。
- **[未知]**：尚无足够证据，不能写成“已经没有”“已经支持”或“开箱即用”。

本轮借助 academic-research-suite 做定向事实核查，并用两项并行核查补充 OmniColPress 和其他作者项目。它不是系统综述，也没有对推荐项目做端到端运行认证。

### 2.1 Visual RAG Toolkit：确有完整流程，推荐理由成立但需补充限制

[论文 v1](https://arxiv.org/html/2602.12510v1)与[作者仓库](https://github.com/Ara-Yeroyan/visual-rag-toolkit)已核查。固定代码提交：`262e01575bd8d9599a98466dce6d12b88f45ea16`，`pyproject.toml` 版本为 `0.2.0`。仓库有实际实现，不只是演示 README：

| 工作 | 代码入口（相对于作者仓库） |
|---|---|
| 本轮首选的统一运行入口 | `benchmarks/vidore_beir_qdrant/run_qdrant_beir.py` |
| BEIR 格式数据加载和 qrels 转换 | `benchmarks/vidore_tatdqa_test/dataset_loader.py` |
| 图像、查询编码和 token 筛选 | `visual_rag/embedding/visual_embedder.py` |
| 行均值、滑动窗口等池化 | `visual_rag/embedding/pooling.py` |
| 实际保存的向量字段和 Qdrant 配置 | `visual_rag/indexing/qdrant_indexer.py` |
| 完整向量和两阶段搜索 | `visual_rag/retrieval/single_stage.py`、`two_stage.py`、`multi_vector.py` |
| 本仓库的评价公式 | `benchmarks/vidore_tatdqa_test/metrics.py` |

例如，一页经 ColPali 得到 32×32=1024 个视觉向量。作者先把每一行的 32 个向量平均成一个，共 32 个，再用窗口大小 3 的既有平滑实现得到 **34 个**向量。先用这 34 个向量筛页面，再用入围页面的 1024 个向量重排。这里的 34 是源码确定的默认 legacy 输出，不能一律写成 32。

它适合学会完整检索链条。它的主实验解决的是检索速度与质量的取舍；完整向量依然保存，所以还不能据此声称实现了整个索引的存储压缩。

### 2.2 Token Pooling：原论文与视觉实现要分开

[原论文](https://arxiv.org/html/2409.14683v1)主要研究 ColBERT 系列的文本多向量检索。[ColPali 官方 HierarchicalTokenPooler](https://github.com/illuin-tech/colpali/blob/3520798500f5d0f54b1d0b6b75104d82c51462a5/colpali_engine/compression/token_pooling/hierarchical_token_pooling.py)是可用的视觉检索池化实现：CPU 聚类、组内平均、归一化，支持返回成员索引。

**这不是原论文全部实验的专用复现仓库。** “相似 token 聚类后取代表”已是现成方法；后续只能作为对照。另需保留前轮的实现发现：所查官方版本把 n×n 距离矩阵作为二维观测传给 SciPy linkage，会再计算这些 n 维观测之间的距离。不能将其成本简单描述为在 128 维向量上做一次 Ward 聚类；更不能直接拼接长文档所有页面后调用。

对于《Towards Storage-Efficient Visual Document Retrieval》，准确表述仍是：**本轮没有确认到完整的作者专用实验仓库；公共 ColPali 代码和池化组件存在。** 不能据此说它“没有代码”，也不能把跑官方池化叫作完整复现其训练与论文全部表格。

### 2.3 OmniColPress：必须修正“涉及训练，所以没法先评价”的印象

[论文](https://arxiv.org/abs/2602.21202)和[作者仓库](https://github.com/hanxiangqin/omni-col-press)存在。已确认公开 AGC、未压缩 ColBERT、Memory Tokens、Sequence Resizing 等 checkpoint，可直接研究它们的评价入口，**无需一开始重做压缩模型训练**。

暂缓的真正理由是运行与比较成本：视觉实验采用 Qwen2.5-VL-3B；仓库涉及 DeepSpeed、FlashAttention、Triton、Liger 等依赖，实际可选与无条件导入应分别看。已见单进程推理分支，所以不能简单说“必须多卡”；但也未证明原生 Windows 可直接装好。

更关键的是输出维度。该路线的相关视觉配置使用 **2048 维**，ColPali 常见检索向量是 **128 维**。在 FP16 下：

`64 × 2048 × 2 = 1024 × 128 × 2 = 262144 bytes = 256 KiB/页`。

因此“只剩 64 个向量”不等于比 ColPali 的 1024 个向量省 16 倍存储。比较必须同时记录维度、数据类型和实际索引字节。详见《核查材料_omnicolpress.md》。

**MAGIC 是本轮新增中最贴近原存储问题的一项。** [论文](https://arxiv.org/abs/2609.21018)完整题名是 *MAGIC: Marginal-Guided Compression with Optimal Transport for Efficient Visual Document Retrieval*；[作者仓库](https://github.com/xandery-geek/MAGIC)固定提交 `be20007d797e5049cd20a9fca870ff119e1413a8`，代码 LICENSE 为 Apache 2.0。其流程是 `scripts/evaluate.py` 生成冻结缓存 → `scripts/magic/build_query_prior.py` 构建先验 → `scripts/magic/eval_magic.py` 压缩并评价；核心是 `magic/magic_compressor.py`，不要求 Qdrant。

用直观例子解释：它先用训练集的一批查询估计“哪些页面向量更常被问题匹配”，再在指定数量内产生代表。代表应保留常用信息，同时覆盖不同内容。评价时直接使用这些代表，不需要把完整向量留在在线索引里重排。因此它比 Toolkit 的主两阶段实验更直接对应存储压缩。

不过，不能把“免训练”理解为“没有额外数据和构建成本”。默认 prior 来自 `vidore/colpali_train_set`，脚本先普通 `load_dataset` 再采样，未设置 streaming；目标约 10000 条查询、20 页，最终保留约 1000 个查询 token。核查当日该数据卡的结构化字段声明 train 为 118195 条、整套 `download_size=52705427788` bytes（约 52.7 GB）。**这不是实测 train-only 下载量，不能据此精确断言该命令一定下载 52.7 GB；但也不能把最终 1000 token 当成只需小文件。** 尚未找到可直接采用的现成 prior/完整缓存。

它的常用 projected 向量为 128 维，压缩核心是普通 PyTorch；单页的成本可能适合本机，但默认 batch 和预处理应另查。初始化会构造 N×N Gram 矩阵，跨采样页建立字典也有这一开销。论文预算用 `ceil`，代码用 `round`，复现时要登记差异。它值得在 Toolkit 的一个完整流程跑通后单独评估，不能在未经单页验证前替换为第二个同时执行的主项目。更多证据见[OmniColPress 与 MAGIC 核查材料](核查材料_omnicolpress.md)。

ColPali-Reproducibility 的[作者代码](https://github.com/JingfenQiao/ColPali-Reproducibility)固定提交 `d42be15f9af2236e312aad476b2bc23d8beced2d`，MIT。它确实值得读，但“标题是复现”不等于运行更省事。已核实的单数据集分支中，`if "非空字符串" or ...` 恒为真；默认空的 matching 类型又没有对应的 score 赋值。另有返回值和池化输出变量问题。作者训练脚本请求 4×RTX A6000、120G 主存；这是作业请求而非实测峰值。使用其已发布 checkpoint 做评价可行性应与完整训练复现分开。

[ModernVBERT 作者代码](https://github.com/illuin-tech/modernvbert)及[公开 ColModernVBERT](https://huggingface.co/ModernVBERT/colmodernvbert)则提供更小的模型。当前模型卡给出 Sentence Transformers `MultiVectorEncoder` 入口；不能直接把它的图像分块当作 ColPali 的 32×32 网格套进现有池化。

这部分的逐项源码、版本、论文与代码状态见《核查材料_其他复现项目.md》。定向检索未找到代码，不是证明不存在；本轮没有穷尽所有后续提交、个人分支和未关联的新仓库。

## 4. Toolkit 在正式跑分前必须处理的具体问题

### 4.1 合法编号 0 被丢弃：已经确认的实际输入问题

固定提交的 `dataset_loader.py::_normalize_qrels` 写成：

```python
qid = _as_str(row.get("query-id") or row.get("query_id") or row.get("qid"))
did = _as_str(row.get("corpus-id") or row.get("corpus_id") or ...)
```

数字 `0` 在 Python 中为假，会被当作“缺失”。官方 Economics 元数据的第一条 query 就是 `query-id=0`，第一条 qrels 是 `query-id=0, corpus-id=63, score=2`。

本轮只提取原函数及其小型辅助函数进行验证：输入三条 qrels（q0/p63、q1/p11、q2/p0），结果只保留 q1。**实际 Economics 存在 q0 触发；p0 是覆盖另一字段的合成例子，当前官方统计显示 Economics 正例页 ID 最小为 6，不能说该数据实际丢了 p0 正例。**

修正范围很小：按字段是否存在且值是否为 `None` 取值，保留整数 0，然后统一字符串化。不要改数据来绕过错误。所读 loader 文本 SHA256 为 `fcfb36c48e285121523d832bd19dbc6aa8ef5e99ba3a0b279a039cb1f6bb686e`。

论文写 Economics 231 题，官方卡写 232 题，这与当前源码行为相容；**没有作者当时运行记录，不能断定历史少一题必然由此造成。** 修复后结果也不应为了贴近论文数字而再删回 231 题。

### 4.2 建库失败不能通过删标签“解决”

运行入口会把未成功建库的页面从 qrels 中移除；默认还会删掉因此没有正例的查询。只设置 `--no-drop-empty-queries` 不够，因为上游可能已经删过页面标签。

首次有效结果的准入条件必须是：**官方 452 页全部建库、页面 ID 集合一致、失败页为 0、删掉的正例为 0、查询数量和 ID 均与官方协议一致**。如果少一页，先修失败，不能直接发表剩余页面上的好看数字。不得使用 `--index-from-queries` 把候选库变成已知正例页集合。

### 4.3 两种“完整向量基线”不是同一个输入

Toolkit 按 `image_token_id` 只取视觉 patch，ColPali 每页为 1024 个。查询先按 attention mask，再按 `input_ids>=4` 过滤；Gemma 的 pad ID=0，因而主动添加的查询增广 token 也会被删。这是作者的 token hygiene 设置，不能混称官方原始 ColPali 的完全相同输入。

首次复现保留作者同一套筛选规则，让 A、B 两组一致；日志必须记录筛选前后 token 数。若以后和官方分数对齐，应另行明确原始 token 协议。不要把旧区域排序缓存的 1031 行直接当成 Toolkit 的 1024 个视觉 patch，也不要把旧区域评分函数当页面 MaxSim。

页面 MaxSim 的含义是：对查询中的每个向量，在该页全部向量中找最相似的一个，再把这些最大相似度相加。旧代码若对每个图像 patch 找最相关查询词，得到的是 patch 分数，聚合方向不同。

### 4.4 单阶段查询池化字段，不会自动得到压缩索引

建库源码同时保存 `initial`、`mean_pooling`、`global_pooling` 和 experimental 字段。默认 ColPali 还可能把同一 34 行池化结果存为 `experimental_pooling` 与 `experimental_pooling_3` 两份。

`single_experimental_tokens` 只决定查询哪个字段，**不会删除 `initial`**。后续若研究存储预算，需另建仅保存压缩表示的 collection，实际统计全部字段、映射、数据库文件/元数据，而不是用“查询了 34 行”代替总存储。这一步属于之后的预算实验，本轮不实施，也不是新算法。

### 4.5 指标核对：发现公式差异，也确认它在首选数据上会抵消

Toolkit 的 nDCG 用 `2**rel-1`；所查官方 ViDoRe `eval_utils.py` 调用 `pytrec_eval` 的 `ndcg_cut`，trec_eval 源码明确默认直接用 rel 作 gain。

但官方 datasets-server 的 Economics qrels 统计（`partial=false`）给出：3628 条记录全部 `score=2`，全部 `fully answerable`。因此两个 gain 只是把所有正例统一乘 3 或乘 2，在 DCG/IDCG 中抵消。**不能把这里的公式差异写成 Economics 已有 nDCG 偏差。** 未来换成混合相关性等级的数据时才需明确统一。

仍需核对查询分母、空结果、排名并列、ID 映射。query ID 和 page ID 是不同命名空间，数字碰巧相同不构成删除该候选的理由；调用通用评价器时要明确 `ignore_identical_ids` 的行为。

### 4.6 论文与示例命令没有提供完整冻结环境

论文报告 FP16、全 RAM、无 HNSW、prefetch=256、top-100；主表 2 使用 3006 页 union。仓库示例存在 FP32、prefetch=200 等不同组合，不能把示例当作表 2 的唯一冻结配置。源码 `initial` 初始配置为 `on_disk=True`，`--ensure-in-ram` 后还必须读取实际 collection 配置确认。

当前论文没有足以复现绝对吞吐的完整硬件/软件记录。其“固定查询长度、减少页面向量带来平方级比较减少”的说法也不准确：固定查询向量数量时，点积数量对页面向量数线性变化。不要沿用这个论证。

## 5. 唯一最小复现单元

**目标：完整跑通一个官方子任务中 A 与 B 的成对对照，得到可信的逐查询排名、指标、耗时和存储记录。** 这是原项目的小规模协议复现，不是论文主表全部数值复现，也不是新方法试验。

| 项目 | 建议固定内容 |
|---|---|
| 作者项目 | Toolkit 固定提交 `262e015…`，单独新环境，保留必要小补丁 |
| 模型 | `vidore/colpali-v1.3`，冻结推理，图像和查询 batch=1 起步，FP16 |
| 数据 | `vidore/economics_reports_v2`，test，全 452 页，完整查询与 qrels；单独 collection |

| A | `single_full`：完整视觉向量上的页面 MaxSim |
| B | `two_stage` + `tokens_vs_experimental_pooling`：34 向量预筛 top-256，完整向量重排 top-100 |

单独 Economics collection 也能避免在多数据集 collection 的预筛阶段先混入其他数据集，再在最终阶段施加过滤造成歧义。

执行顺序只设这一条：

1. 固定代码、模型、数据版本；修 0-ID；给建库完整性与指标添加小型验收。只安装主入口需要的组件，不先部署 UI、Cloudinary 或 PDF 转图。
2. 先做一个页面和一个查询的推理检查，确认真实 shape、token 筛选和有限值；再用少量页面计时/测峰值。这只是环境检查，不报告效果。
3. 编码并建好**完整 452 页**。可以先用包含 q0 的 10 个问题验证检索链条，但候选库仍是完整 452 页；之后评价完整官方查询集合。官方卡为 232 题，完整下载后核对每题标签，异常必须解释，不能默默过滤。
4. A、B 各执行正式评价，记录一致配置。计时先预热；如需比较速度，对相同已编码查询做相同次数的搜索计时，同时保留包括编码在内的端到端时间。
5. 成功后再决定是否扩展到论文 3006 页 union 以检查规模效应。此时才考虑独立“只存池化向量”的预算对照；不在首次跑通阶段同时启动新的自适应/跨页机制。

可复用的 CLI 参数已在源码确认：`--index --batch-size 1 --torch-dtype float16 --qdrant-vector-dtype float16 --no-cloudinary --no-eval --pooling-windows 3 --experimental-pooling-kernel legacy --indexing-threshold 0 --full-scan-threshold 0 --ensure-in-ram`；评价使用表中 mode、`--prefetch-k 256 --top-k 100 --evaluation-scope per_dataset --no-drop-empty-queries`。**这只是待实现配置清单，不是当前无补丁即可运行的安装命令。** 模型/数据 revision 传递和失败即停止仍需小补丁，Qdrant 服务地址也尚未配置。

## 7. 本机资源与时间：先给可检查的估算

以下均为推导和时间预算，不是本机测量。前轮本机 RAM 记录为约 31.83 GiB。

### 存储与显存

452 页、128 维、FP16：

| 内容 | 裸向量量，不含数据库开销 |
|---|---:|
| 每页完整 1024 向量 | 113 MiB |
| 每页 32 行均值 | 3.53125 MiB |
| 每页 34 个 Conv1d 向量 | 3.751953125 MiB |
| 默认完整 + 行均值 + 单全局 + 两份 34 向量 | 约 124.15 MiB |

实际还要算数据库存储结构、payload、页 ID、运行缓存、WAL、元数据等；磁盘大小、常驻 RAM 和 GPU 显存是三种不同量。应另外记录模型和下载缓存，但不能把它们混称在线检索索引。

ColPali 约 2.925B 参数的半精度基础权重约 5.45 GiB，外加 adapter、激活、CUDA 分配和图片输入。12GB 显存可能容纳 batch=1 冻结推理，但本轮没有峰值证据。Qdrant 在本机主要消耗 CPU/RAM，不要求把全部索引放进显存。

数据的 55 MB 是压缩文件大小；Toolkit loader 会解码页面并保存在 Python 列表，不能据 55 MB 推断运行 RAM。最小检查需测这一项；如果逼近可用主存，再判断是否仅需小范围改为按批读取。

### 小库不会自动复现四倍加速

设查询长度相同，忽略预筛/数据库开销，A 的相似度计算量正比于 `452×1024`；B 约为 `452×34 + 256×1024`，是 A 的 **约 60%**。即使只算点积，理想比值也约 1.67 倍，而非 4 倍；真实端到端还包含查询编码与服务开销。

论文 3006 页 union 下，该比例约为 11.84%，所以规模变化很重要。首次 452 页实验应验收正确性和可运行性；若没有四倍加速，不能直接判复现失败，也不能为了追倍数偷偷改候选集合或预筛数量。

### 耗时预算与停止条件

- **环境和小修：最多先投入 1–2 个工作日。** 这是项目管理上限，不是安装时长保证。若必须大规模迁移 Linux 专用内核或重写检索服务，停止扩大修补，返回选择更直接的官方评价入口。
- **编码时间用实测外推。** 若单页 0.5/2/5 秒，452 页分别约 3.8/15.1/37.7 分钟，未含加载、上传和序列化。先用少量页测量，再据实际速率估计。
- **首次完整 A/B 对照：预算半天进行运行和结果核验**，包括异常修复和记录；若实测外推显著超出预算，再决定是否继续，不能把纸面估算当完成承诺。下载速度取决于网络，约 6GB 模型下载另计。
- **立即停止有效跑分的条件**：0-ID 仍丢失；候选页/正例被删；A/B 输入 token 或图片不一致；出现 NaN；ID 无法对应；实际数据库配置不符合记录。这些需修正后重跑，不能过滤异常后继续报告。
- **暂停此底座的条件**：batch=1 仍无法在显存中稳定推理，或图片全量解码导致持续换页/主存压力，或超过两天仍卡在服务/依赖；此时再评估公开小模型或官方直接评价。不要同时维护两套未跑通环境。
- **不属于停止条件**：分数未提升、两阶段略有召回损失、452 页没有论文大库速度倍数。复现是如实观察已有方法，不是要求结果一定更好。

首次验收应交付：固定环境/版本清单、小补丁 diff、数据与索引 ID 核对、配置快照、逐查询结果、A/B 指标和资源记录。随后才能判断是否适合围绕预算提出一个小而清晰的研究问题。现成池化、两阶段检索、两档容量或拼接矩阵本身均不作为创新。
